# Light-bar protocol of the 1MORE Spearhead VR

Reverse-engineered from USB traffic of the vendor Windows panel ("1MORE Spearhead VR Settings", driver package H1005 SpearheadVR DRIVER 2.14 WHQL). Observed on one unit only; everything here is what was seen, not documentation from the vendor. Items marked **(guess)** are interpretations.

## Device

- USB `0d8c:0172` (C-Media), product string `1MORE Spearhead VR `, `bcdDevice 1.16`, full speed.
- Audio interfaces (class 1) are handled by `snd-usb-audio`. Playback is 2 channels at Linux level; the "7.1" shown by the Windows panel is not a hardware feature visible to Linux.
- One HID interface (interface 3, class 3) with a single interrupt IN endpoint (`0x87`) and no OUT endpoint, so output reports go over the control endpoint.

HID report descriptor (91 bytes):

```
050c0901a10185011500250109e909ea7501950281420601ff0901950a8106050c09cd09b709b5

```

It declares report ID `1` (consumer-control inputs plus vendor fields) and report IDs `0xFF` and `0xF2` (vendor page `0xFF07`, 15 data bytes in and out). The light bar is controlled through report ID `0xFF`.

## Transport

Each frame is a 16-byte `SET_REPORT` (output) on interface 3:

```
bmRequestType 0x21, bRequest 0x09, wValue 0x02FF (output, report ID 0xFF),
wIndex 3, wLength 16
```

On Linux, `write()` of the 16 bytes (report ID first) to the device's `/dev/hidrawN` produces exactly this transfer.

## Command sequence

One lighting update is 35 frames, sent back to back:

| # | Bytes (hex) | Meaning |
|---|---|---|
| 1 | `ff 02` + 14×`00` | start **(guess)** |
| 2 | `ff 03` + header (2 or 4 bytes) + zero padding | mode header, see below |
| 3–34 | `ff 04 OO 00` + 12 data bytes | table block `i = 0..31`, `OO = 4·i` |
| 35 | `ff 01` + 14×`00` | end / commit **(guess)** |

Blocks 3–34 carry a 384-byte table, 12 bytes per frame.

### Mode header (frame 2)

| Mode | Bytes after `ff 03` | Notes |
|---|---|---|
| constant | `00 01 00 00` | with an all-zero table this is "lights off" |
| breathe | `02 80 00 SS` | `SS` is the speed: `0x0a` = fast … `0x32` = middle … `0x64` = slow |
| heartbeat | `03 80 00 00` | all four speed positions of the vendor panel produced this identical header |

Speed values seen: `0x64` down to `0x5c` while dragging the slider, and the extremes `0x0a` and `0x64`. The direction (smaller = faster) was inferred from the order of events and from a hardware check of `0x64` being the slow setting; values between 10 and 100 are accepted by the tool, the range limits themselves come from the slider ends observed in the capture.

### Colour table (frames 3–34)

The table is 128 entries of 3 bytes (R, G, B), a linear ramp from the chosen colour down to black:

```
entry[i] = floor(colour_channel * (127 - i) / 127)     i = 0..127, per channel
```

Checked against captured tables for two colours (the panel's own green `(3,255,4)` and blue `(4,102,217)`): zero mismatching bytes. Pure colours generated by this formula were also checked on the hardware.

The table was identical in every capture for a given colour, regardless of mode and speed; only the header changes the mode.

## What else was seen on the bus (not used)

- **Mic mute** is a standard USB Audio Class request: `SET_CUR` mute control on feature unit 6 (`wValue 0x0100`, `wIndex 0x0600`), value `01` / `00`.
- **Volume** is standard UAC `SET_CUR` on feature unit 5 (`wValue 0x0201` / `0x0202`, `wIndex 0x0500`).
- At startup the panel writes four 16-byte output reports with report ID `1` (`wValue 0x0201`, e.g. `01000000 0048010c …`, `01000000 00ff0149 …`) that look like register/value pairs **(guess)**, reads report ID `1` back with `GET_REPORT`, and sends one `f2 00 …` frame. The tool does not use any of these, and their purpose is unknown. They were left alone on purpose.
- The Windows panel also offers a firmware update tool. It was not used and is not related to this protocol.

## How it was captured

- Linux host with the headphones passed through to a Windows VM (libvirt/QEMU).
- `usbmon` on the host (`/sys/kernel/debug/usb/usbmon/<bus>u`), filtered for control OUT transfers to the device, with timestamped markers written before each panel action.
- One panel parameter changed at a time, then the resulting frames were aligned with the markers and compared byte by byte.
- The generated frames of this tool were compared against the captured frames for breathe (speeds `0x64`, `0x0a`, `0x32`), constant and heartbeat: identical.
